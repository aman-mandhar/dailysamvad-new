# Phase 14C — Schema.org Structured Data and JSON-LD

## Objective

Implement complete, valid, Laravel-native Schema.org structured data for the public news portal using JSON-LD.

Phase 14A established the native SEO foundation.

Phase 14B added OpenGraph and Twitter/X metadata.

Phase 14C must extend the same SEO architecture and introduce structured data without creating a separate competing SEO system.

Implement structured data for:

* Website
* Organization or NewsMediaOrganization
* NewsArticle
* BreadcrumbList
* Person
* CollectionPage
* SearchResultsPage
* WebPage
* ImageObject
* VideoObject when applicable

The implementation must be valid, secure, reusable, testable, and compatible with Google Search structured-data requirements.

Implement only Phase 14C.

Do not implement XML sitemaps, news sitemaps, image sitemaps, robots.txt changes, Google News optimization, Google Discover optimization, or Phase 14D.

---

Audit:

* Phase 14A SEO manager and metadata DTOs
* Phase 14B OpenGraph and Twitter/X implementation
* Shared SEO Blade component or partial

* Existing JSON-LD scripts
* Existing SEO tests

Reuse and extend the current SEO architecture.

* Duplicate page-context logic
* Duplicate title or description resolvers
* Duplicate canonical URL logic
* Duplicate social-image logic
* Per-page JSON-LD blocks scattered across Blade templates
* Conflicting structured-data graphs

If structured data already exists, audit it and consolidate it into the native SEO layer.

## 2. Architecture Requirements

Structured data must be generated by the native SEO layer.

A suitable architecture may include:

```text
app/
    SEO/
        SEOManager.php
        SEOData.php
        StructuredData/
            SchemaGraph.php
            SchemaNode.php
            WebsiteSchema.php
            OrganizationSchema.php
            NewsArticleSchema.php
            BreadcrumbSchema.php
            PersonSchema.php
            CollectionPageSchema.php
            ImageObjectSchema.php
            VideoObjectSchema.php
```

These names are examples only.

Use the existing project structure and naming conventions.

The preferred result is one resolved JSON-LD graph containing relevant nodes for the current page.

Example concept:

```json
{
  "@context": "https://schema.org",
  "@graph": [
    {},
    {},
    {}
  ]
}
```

Do not force an `@graph` structure if the existing architecture has a cleaner tested approach, but avoid emitting multiple conflicting JSON-LD scripts.

Structured-data generation must not live inside controllers.

Blade must only render the final serialized structured-data payload.

## 3. General JSON-LD Requirements

Render structured data using:

```html
<script type="application/ld+json">
...
</script>
```

Requirements:

* Valid JSON
* Valid UTF-8
* Valid Schema.org properties
* No trailing commas
* No comments
* No HTML markup inside JSON values
* No empty properties
* No `null` values
* No invalid URLs
* No filesystem paths
* No private author data
* No draft content
* No duplicate top-level entities
* No fabricated data
* No unsupported or misleading properties

Use Laravel JSON serialization rather than manually concatenating JSON strings.

The final JSON-LD must be safely encoded.

Do not use unescaped manual string construction.

## 4. Schema Graph Identity

Use stable `@id` values to connect schema nodes.

Suggested identity pattern:

```text
https://example.com/#website
https://example.com/#organization
https://example.com/article-slug/#article
https://example.com/article-slug/#webpage
https://example.com/article-slug/#breadcrumb
https://example.com/author/name/#person
https://example.com/media/image.jpg/#primaryimage
```

Requirements:

* Use absolute canonical URLs
* Reuse Phase 14A canonical URLs
* Do not hardcode the production domain
* Avoid duplicate slash variations
* Avoid query-string tracking parameters
* Use predictable fragment identifiers
* Reuse the same identity for the same entity
* Do not create circular or conflicting IDs

Schema nodes should reference each other through `@id` where appropriate.

## 5. Website Schema

Generate a `WebSite` entity for public pages.

Example structure:

```json
{
  "@type": "WebSite",
  "@id": "https://example.com/#website",
  "url": "https://example.com/",
  "name": "Site Name",
  "description": "Site description",
  "publisher": {
    "@id": "https://example.com/#organization"
  },
  "inLanguage": "en-IN"
}
```

Support `potentialAction` with `SearchAction` only when a working public search route exists.

Example:

```json
{
  "@type": "SearchAction",
  "target": {
    "@type": "EntryPoint",
    "urlTemplate": "https://example.com/search?q={search_term_string}"
  },
  "query-input": "required name=search_term_string"
}
```

Requirements:

* Use the real public search route
* Use the actual query parameter name
* Use an absolute URL template
* Do not add SearchAction when search is unavailable
* Do not invent a search endpoint
* Do not expose admin search routes
* Do not include malformed placeholders

## 11. NewsArticle Schema

Published article pages must generate a `NewsArticle` entity.

Example structure:

```json
{
  "@type": "NewsArticle",
  "@id": "https://example.com/article-slug/#article",
  "mainEntityOfPage": {
    "@id": "https://example.com/article-slug/#webpage"
  },
  "headline": "Article headline",
  "description": "Article description",
  "datePublished": "2026-07-19T18:30:00+05:30",
  "dateModified": "2026-07-19T19:00:00+05:30",
  "author": {
    "@id": "https://example.com/author/name/#person"
  },
  "publisher": {
    "@id": "https://example.com/#organization"
  },
  "image": {
    "@id": "https://example.com/article-slug/#primaryimage"
  },
  "articleSection": "Punjab",
  "keywords": [
    "Punjab",
    "Politics"
  ],
  "inLanguage": "pa-IN",
  "isPartOf": {
    "@id": "https://example.com/#website"
  }
}
```

Only render `NewsArticle` for public, published news content.

Do not render it for:

* Drafts
* Scheduled unpublished posts
* Private posts
* Preview URLs
* Category archives
* Tag archives
* Author archives
* Search pages
* Static pages

## 24. BreadcrumbList Schema

Generate a `BreadcrumbList` that matches the visible or logical breadcrumb hierarchy.

Example article hierarchy:

```text

Category
Article
```

Example schema:

```json
{
  "@type": "BreadcrumbList",
  "@id": "https://example.com/article-slug/#breadcrumb",
  "itemListElement": [
    {
      "@type": "ListItem",
      "position": 1,
      "name": "Home",
      "item": "https://example.com/"
    },
    {
      "@type": "ListItem",
      "position": 2,
      "name": "Punjab",
      "item": "https://example.com/category/punjab/"
    },
    {
      "@type": "ListItem",
      "position": 3,
      "name": "Article title",
      "item": "https://example.com/article-slug/"
    }
  ]
}
```

Requirements:

* Positions start at 1
* Positions are sequential
* URLs are absolute
* Names are plain text
* URLs match public routes
* Final item should use the canonical page URL
* Do not include admin routes
* Do not invent category URLs
* Avoid duplicate breadcrumb items
* Match existing visible breadcrumbs where they exist

Use the primary category for article breadcrumbs.

## 37. URL Validation

All structured-data URLs must be:

* Absolute
* HTTP or HTTPS
* Publicly resolvable in production
* Correctly encoded
* Free from backslashes
* Free from control characters
* Free from duplicated hosts
* Free from local filesystem paths

Reject unsafe schemes such as:

```text

data:
file:
ftp:
```

Relative public paths may be converted using the configured application host.

* Quotes
* Apostrophes
* Ampersands
* Punjabi text
* Hindi text
* `</script>` sequences
